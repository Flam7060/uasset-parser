# native_calls — граф вызовов нативного кода

## Зачем

ark-re уже называет нативные функции по PDB (`calls[].native` в `asset_function`,
`pdb_type`, `pdb_symbols`): для символа есть имя, RVA и `size`. Чего нет — рёбер
**между** нативными функциями, «кто кого зовёт». Это читается только из тела функции
(машкода), которое сейчас не разбирается.

Разбор самой игры (`docs/game/native_inventory_multiuse_trust.md`) состоит из
кандидатов, которые без чтения тел нельзя ни подтвердить, ни опровергнуть — там прямо
помечено «тела (asm) не читались». `native_calls(symbol)` закрывает этот разрыв для
прямых вызовов: отдаёт **структурные факты** — рёбра графа вызовов, резолвнутые в имена
по нашей же карте символов, — по духу как `asset_function` отдаёт `calls[]` для
блюпринтов.

Это анализ структуры кода («какой символ что зовёт»), а не сырой листинг. Сырой
дизасм, если понадобится, пишется в файл, который открываешь сам, а не вываливается в
чат.

## Что строим

- `arkre/disasm.py` — модуль: PE-секции EXE → файловое смещение по RVA, дизасм тела,
  резолв целей по таблице символов.
- `native_calls(symbol)` — инструмент в `server.py` (+ описание, как у `asset_function`).
- CLI-обёртка.
- Тест.

Одна фича, один коммит (feat и test раздельно, как в истории репозитория).

## Поток

1. `symbol` → `(rva, size)` из таблицы символов PDB (уже есть).
2. `rva` → файловое смещение по таблице секций PE `ShooterGameServer.exe`, читаем `size`
   байт. (`pdb.py::_section_rvas` даёт секции из PDB; для EXE нужен разбор PE optional
   header + section table — отдельная мелкая функция.)
3. Дизасм линейным проходом от входа (iced-x86), x86-64.
4. Прямой `call rel32`: `target_rva = rva(след. инструкции) + disp` → имя по карте
   символов (ближайший символ ≤ target с оффсетом, `Foo+0x40`). Ребро в `calls[]`.
5. `call [rip+disp]` → цель в IAT → имя импортируемой функции (import-тунк).
6. `call [reg+disp]` — кандидат на виртуальный: если по `.rdata` слот ложится на известную
   vtable и в точке вызова восстановим тип — называем; иначе `indirect{kind:vtable}`.
   `call reg` без восстановимого типа — `indirect{kind:reg}`.
7. Обращения к данным (`mov`/`lea` на глобал по `[rip+disp]`) → `reads[]`/`writes[]` по
   карте символов данных.

## Выход (факты, не листинг)

```json
{
  "symbol": "...", "rva": "0x...", "size": 1234,
  "calls":    [{"rva": "0x...", "name": "...", "kind": "direct"}],
  "reads":    [{"rva": "0x...", "name": "...", "note": "глобал/поле"}],
  "writes":   [{"rva": "0x...", "name": "...", "note": "глобал/поле"}],
  "indirect": [{"site": "0x...", "kind": "vtable|reg", "name": "... если резолвнут"}],
  "unresolved":[{"rva": "0x...", "note": "цель вне известных символов"}]
}
```

## Ограничения (честно)

- Виртуальные вызовы называются **только там, где в точке вызова статически восстановим
  тип** объекта (регистр привязан к известной vtable). Полное разрешение требует
  трассировки типов, которой в v1 нет: остальные виртуальные остаются
  `indirect{vtable, слот N}` — классифицированы, не названы.
- Линейный проход надёжен для извлечения `call` при известном `size`; данные-в-коде и
  джамп-таблицы могут дать локальный рассинхрон. Для графа вызовов терпимо;
  recursive-descent точнее, но дороже.
- Покрытие именами — только то, что есть в PDB; цель в безымянной области отдаётся как
  RVA.
- Зависимость: `+ iced-x86` в deps uv-скрипта (одна строка).

## Решено (уточнение 2026-11-01)

- **Движок:** `iced-x86` (точный x64, удобный flow-control / branch-target API).
- **Форма фактов:** `calls[]` + `reads[]`/`writes[]` сразу, как у `asset_function`.
- **Резолв целей:** ближайший символ + оффсет (`Foo+0x40`).

## Про «быстро vs нормально» и объём

Рантайм A и B одинаков — **миллисекунды на символ**, никакой «лишней минуты на вызов»
нет. vtable-резолв — разовый разбор `.rdata` при первом обращении, дальше из кеша.
«Дольше» про полную версию — это дольше **писать** (больше кода: PE-парсер IAT + таблиц
vtable), а не медленнее работать.

Честный предел: виртуальный вызов называется только там, где в точке вызова статически
виден тип объекта; полностью «назвать все виртуальные» без трассировки типов нельзя.
Поэтому полная версия — это «прямые + импорты + виртуальные где тип ясен, остальные
классифицированы», а не «все гейты раскрыты».

**Рекомендация:** раз нужен нормальный тул, а не заглушка — делаем сразу полный разбор
(прямые + import-тунки + vtable где тип восстановим + reads/writes), с честной разметкой
нерезолвнутого. Один модуль ~250–350 строк + PE-парсер IAT/.rdata.

## Зафиксировано для v1 (вариант B)

- **Объём:** B — прямые вызовы + import-тунки + vtable-резолв где тип восстановим +
  `reads[]`/`writes[]`.
- **Глубина:** 1 (прямые callee символа); транзитивный граф — отдельной итерацией.
- **Бинарь:** только сервер (`ShooterGameServer.exe`); клиент — позже тем же кодом.
- **Кеш:** на лету, без persist в sqlite (функция дешёвая).
- **Золотой тест:** агент выбирает стабильную серверную точку входа из подтверждённого
  списка (`pdb_symbols kind=function`); тест skip без бинаря/PDB.

## Критерий готовности v1

Для заданного серверного символа с известным `size` `native_calls` возвращает прямые
вызовы с именами (где цель в карте символов), импорты — по IAT, виртуальные — названными
где vtable локально восстановима либо классифицированными (`vtable`, слот N); `reads[]`/
`writes[]` заполнены; тест на золотой паре зелёный; сырой листинг в чат не попадает.

# Implementation brief (для холодного агента)

Агент стартует без контекста этой сессии — ниже всё нужное со ссылками на существующий
код. Весь анализ — **статическое чтение файла `.exe` с диска**.

## Что переиспользовать (ark-re)

- **Пути:** `arkre/config.py`. Есть `pdb_server()`/`pdb_client()`, `game_dir()`. **Пути к
  .exe нет** — добавить `server_exe()` (env `ARK_SERVER_EXE`, дефолт —
  `ShooterGameServer.exe` рядом с `pdb_server()`), по аналогии `client_exe()`.
- **Символы PDB:** `arkre/pdb.py` импортирует PDB в sqlite; `pdb.pdb_symbols(query, kind,
  pdb_name, limit)` отдаёт имя+RVA+size. Для резолва нужна полная карта: разово выбрать все
  символы (function+data), отсортировать по RVA, bisect по target. Vtable-символы — data с
  именем вида `??_7<Class>@@6B@`.
- **Секции:** `pdb._section_rvas()` даёт **виртуальные** адреса секций из PDB — этого НЕ
  хватает: для RVA→файловое смещение нужна таблица секций самого `.exe`
  (`PointerToRawData`). Парсить PE (ниже).
- **Регистрация инструмента:** `server.py`, декоратор `@tool`, возврат `respond.fit(dict)`
  (JSON ≤20k, сам ужимает длинные списки). Ошибки — поднять `pdb.PdbError`/`ValueError`
  (уже в `_USER_ERRORS` → уходят агенту русским текстом).
- **Форма вывода:** держать в духе `asset_tools.asset_function` (`calls`/`reads`/`writes`).
- **Зависимость:** `iced-x86` добавить в inline-deps `server.py`
  (`# dependencies = [...]`). Импортировать iced **лениво внутри `disasm.py`** (import в
  функции; если нет — `PdbError("нет iced-x86…")`), чтобы остальной arkre импортировался
  без неё (ядро сейчас бездепендентное).

## PE-парсер (минимум, в disasm.py)

По `ShooterGameServer.exe`: DOS-заголовок (`e_lfanew`) → PE-сигнатура → COFF → **Optional
Header** (`ImageBase`, `NumberOfSections`, DataDirectory: Import #1, IAT #12) → **таблица
секций** (`VirtualAddress`, `VirtualSize`, `PointerToRawData`, `SizeOfRawData`, имя).

- `rva2off(rva)` — секция, где `VA <= rva < VA+VirtualSize`, вернуть
  `PointerToRawData + (rva-VA)`.
- Найти `.text` (код), `.rdata` (vtable), импорт-директорию (имена импортов по RVA слотов
  IAT).

## Алгоритм (на один символ)

1. `(rva,size)` символа из PDB; байты = read(`exe`, `rva2off(rva)`, `size`).
2. iced `Decoder(64, bytes, ip=ImageBase+rva)`. По каждой инструкции (атрибуты iced
   сверить по докам — `flow_control`, near-branch target, ip-rel memory, `memory_base`,
   `memory_displacement`):
   - прямой `call rel32` → target VA → rva (`−ImageBase`) → ближайший символ+оффсет →
     `calls[]{kind:direct}`;
   - `call [rip+disp]` (ip-rel память) → адрес слота IAT → имя импорта →
     `calls[]{kind:import}`;
   - `call [reg+disp]` → если reg ранее в функции загружен из известной vftable
     (`lea/mov reg,[rip+vtable_rva]`, `vtable_rva` ∈ data-символы `??_7`), slot =
     `disp/8`, прочитать из `.rdata` 8 байт слота → `(VA−ImageBase)` → символ →
     `calls[]{kind:virtual}`; иначе `indirect[]{kind:vtable, slot}`;
   - `call reg` без восстановимого источника → `indirect[]{kind:reg}`;
   - `mov/lea` на глобал по `[rip+disp]`, цель ∈ data-символы → `reads[]`/`writes[]`
     (`write`, если мнемоника пишет в память).
3. Цель вне карты символов → `unresolved[]` с RVA.

## Файлы и API

- `arkre/disasm.py`: `native_calls(symbol: str, pdb_name: str = "server") -> dict`
  (+ внутренние `_pe_sections`, `_rva2off`, `_symbol_index`, `_resolve`). Стиль arkre,
  комментарии по-русски.
- `server.py`: `@tool def native_calls(symbol, pdb_name="server") -> str:
  return respond.fit(disasm.native_calls(symbol, pdb_name))` с докстрингом (что отдаёт +
  ограничения: виртуальные названы не все).
- CLI: как у прочих инструментов; сырой листинг — только в файл по отдельному флагу, не в
  stdout по умолчанию.

## Тесты (skippable без бинаря)

- Синтетика: крошечный буфер с `call rel32` на известный оффсет + `call [rip+disp]`;
  проверить резолв прямого и классификацию непрямого (ImageBase/секции замокать).
- Реальный (`@skipUnless` наличия `server_exe()`+PDB): стабильная серверная точка входа —
  `calls[]` непустой и содержит ожидаемое имя; виртуальные — названы или классифицированы.
