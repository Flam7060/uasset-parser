# Structures Kav (3461528683): баг-репорт по серверным RPC

_2026-10-28 · статический разбор байткода, на живом сервере не проверялось_

## Сводка

Сравнение Kav (форк S+, заявлен как «починенный») с оригинальным Structures Plus
(731604991) по псевдокоду серверных функций. Три находки из отчёта по S+
([Structures_Plus_S_731604991.md](Structures_Plus_S_731604991.md)) — доверие к
клиентским `UI_Data` в Propagator — **в Kav не устранены**, байткод идентичен
байт-в-байт после нормализации. Новая находка — доверие к результату `RemoveItem`
без проверки в `BP_Converter` — присутствует **в обоих модах**, в Kav не исправлена.

Отдельно найдена новая уязвимость (#7) в инструменте OmniTool: режим Basic
Transfer переносит предметы из контейнера, ссылку на который присылает клиент,
без проверки команды и `AllowStructureAccess` — при модифицированном клиенте это
кража из чужих структур в радиусе `PullRange`, сквозь стены. Добавленный Kav
анти-тампер (`SessionID` / `Cheater()`, см. раздел «Доп. защита Kav») её не
закрывает.

сервере ничего не запускалось и не проверялось: вероятность срабатывания,
точные числа и побочные эффекты (п. 1 про `K2_DestroyComponent`) не
подтверждены, только выведены из кода.

## 1. Converter: конвертация не проверяет списание исходного предмета

**Серьёзность: высокая.** **Уверенность: по коду высокая, по игре не
подтверждено.**

### Затронутый код

`Misc/Converter/BP_Converter.uasset` → `BPServerHandleNetExecCommand`
(команда `ItemConversionData`) → `ConvertSelectedItem`.

### Механизм

`BPServerHandleNetExecCommand` принимает от клиента два параметра без проверки,
что они относятся к текущей структуре-конвертеру: `ExecParams.ObjParam1`
(`PrimalInventoryComponent`) и `ExecParams.ObjParam2` (`PrimalItem`). Дальше:

1. Таблица допустимых конверсий (`ItemMappings`) собирается из дефолтных
   предметов переданного `ObjParam1`, а не из инвентаря самого конвертера.
2. `ConvertSelectedItem(PC, Item)` вызывается с переданным `ObjParam2`.
3. В `ConvertSelectedItem`: `RemoveItem(Item.ItemID)` из инвентаря конвертера,
   затем `BPIncrementItemTemplateQuantity(ToClass, Item.ItemQuantity)` того же
   инвентаря — **без проверки булева результата `RemoveItem`**.
4. Клиентский `ObjParam1` уничтожается через `K2_DestroyComponent`.

Ограничители, которые остаются в силе: пара классов должна пройти
`AreCraftingRequirementsIdentical`, игрок должен иметь нужный энграм
(`HasEngram`), конверсия не должна быть в `DisabledConversions`.

### Ожидаемое влияние

Если `RemoveItem` может не найти переданный `Item` в инвентаре конвертера
(предмет лежит не там, куда его ищут) — список выдаётся, списание тихо
проваливается: дублирование предмета. Степень влияния зависит от того, как
широко `BPFindItemWithID`/контекст вызова допускают несовпадающий инвентарь —
это не проверено на сервере.

Отдельно: `K2_DestroyComponent` на произвольном клиентском `ObjParam1` —
потенциальное уничтожение чужого инвентарного компонента (DoS), механизм
того же вызова, воспроизводимость не проверялась.

### Рекомендация по фиксу

- Проверять булев результат `RemoveItem` перед `BPIncrementItemTemplateQuantity`;
  при `false` — прерывать выполнение и не выдавать результат.
- Не принимать произвольный `ObjParam1`/`ObjParam2` от клиента: брать инвентарь
  и предмет из состояния самого актора-конвертера на сервере, а не из RPC-параметров.

## 2. Propagator: клиентские `UI_Data` без проверки доступа и клампа

**Серьёзность: средняя.** Подробности и механизм — в отдельном отчёте
([Structures_Plus_S_731604991.md](Structures_Plus_S_731604991.md), раздел
«Находки»): `PropagatorStart` → `ApplyModifications` копирует клиентские
`CurGender`/`CurCanBreed`/`PulseCount` без проверки `SP_GetAccessLevel` и без
клампа по `PulseMax`; `PulseMax`/`PropagatorDisableDinoMods` используются
только в клиентском виджете, сервер их не читает.

**Статус в Kav:** код `BPServerHandleNetExecCommand`, `ApplyModifications`,
`DoMating_-_MutateStats` в `BP_Propagator.uasset` идентичен S+ после
нормализации меток переходов. Единственное изменение — новый выключатель
`[KavStructures] DisablePropagator`, который уничтожает актор целиком при
старте сервера (административный рубильник, не фикс логики).

### Рекомендация по фиксу
См. отчёт по S+: проверка `SP_GetAccessLevel` перед применением, кламп
`PulseCount` по `PulseMax`, чтение `PropagatorDisableDinoMods` на сервере.

## 3. ChibiDisplay: выбор чибика не проверяет списание исходного предмета

**Серьёзность: средняя.** **Уверенность: по коду высокая, по игре не
подтверждено.**

### Затронутый код
`BP_ChibiDisplay.uasset` → `BPServerHandleNetExecCommand` (команда
`SelectChibi`) → `SelectChibi(PC, ChibiItem)`.

### Механизм
`SelectChibi` вызывает `RemoveItem(ChibiItem.ItemID)` из инвентаря персонажа
игрока, затем безусловно `AddItemObjectEx(ChibiItem, …)` в инвентарь дисплея —
результат `RemoveItem` не проверяется. Шаблон идентичен п. 1, только без
смены класса предмета.

### Ожидаемое влияние
Если `RemoveItem` может провалиться (предмет не в инвентаре персонажа,
переданном вызовом), предмет окажется одновременно у игрока и в дисплее —
дублирование. Ценность предмета (скин-чибик) ниже, чем в п. 1.

### Рекомендация по фиксу
Проверять результат `RemoveItem`, прерывать при `false`.

## 4. ItemTranslocator: назначение адресата без проверки владельца

**Серьёзность: низкая.** **Уверенность: по коду высокая, по игре не
подтверждено.**

### Затронутый код
`BP_ItemTranslocator.uasset` → `BPServerHandleNetExecCommand` (команда
`SetDestination`) → `SetDestination(NewDestination, DestinationName)`.

### Механизм
`SetDestination` принимает `ExecParams.ObjParam1` как `NewDestination` без
проверки, принадлежит ли этот транслокатор вызывающему игроку или его племени;
проверяется только `IsValid`. Присваивает `LinkedTranslocator` переданный
объект.

### Ожидаемое влияние
Не дюп: это кража маршрута — чужой автоматический транслокатор можно
перенаправить на свою структуру, если известен адрес/ссылка на него. Степень
влияния зависит от того, насколько легко клиенту получить ссылку на чужой
актор — не проверялось.

### Рекомендация по фиксу
Проверять принадлежность `NewDestination` тому же племени/владельцу, что и
вызывающий игрок, перед присваиванием.

## 5. HitchingPost: иммобилайз произвольного дино из RPC

**Серьёзность: средняя.** **Уверенность: пробел в коде — высокая, итоговое
влияние — зависит от баффа, не проверено.**

### Затронутый код
`Misc/HitchingPost/BP_HitchingPost.uasset` → `BPServerHandleNetExecCommand`
(команды `Hitch` / `Unhitch`) → `ToggleHitchDino(Dino, DoHitch)`. Код
идентичен в S+ (731604991) и Kav — находка общая.

### Механизм
Обработчик берёт `ExecParams.ObjParam1`, проверяет только `IsValid` и приведение
к `PrimalDinoCharacter`, и передаёт его прямо в `ToggleHitchDino`, который вешает
`Buff_HitchingImmobilize_C` (обездвиживание). Правильный фильтр в моде есть —
`GetNearbyDinos` отбирает только дино **своей команды** (`TargetingTeam`) в радиусе
`HitchRadius` — но его результат используется лишь для подсчёта лимита
(`FilterDinosByHitchStatus` → `DinoLimit`), а не для проверки, что `ObjParam1`
входит в этот набор.

### Ожидаемое влияние
Модифицированный клиент может передать ссылку на дино **любой команды и на любом
расстоянии** и применить к нему обездвиживающий бафф — удалённая заморозка чужого
дино (PvP-грифинг). Оговорка: не проверено, не перепроверяет ли сам
`Buff_HitchingImmobilize` принадлежность команды при `StaticAddBuff`; если
перепроверяет — влияние снижается до «своих» дино.

### Рекомендация по фиксу
Проверять, что `ObjParam1` входит в отфильтрованный `GetNearbyDinos` (та же
проверка команды и радиуса), прежде чем вызывать `ToggleHitchDino`.

## 6. StarterBlock: сдвиг/поворот структуры по RPC без ограничений

**Серьёзность: низкая.** **Уверенность: по коду высокая, влияние не проверено.**

### Затронутый код
`Misc/StarterBlock/BP_StarterBlock.uasset` → `BPServerHandleNetExecCommand`
(команды `UpdatePos_Server` / `UpdateRot_Server`). Код идентичен в S+ и Kav.

### Механизм
Обработчик принимает `FloatParam1..3` от клиента и подаёт их прямо в
`UpdatePosition` / `UpdateRotation` без клампа смещения и без проверки диапазона.
Нативный диспетчер `BPServerHandleNetExecCommand` гейтит доступ по праву
использования структуры, но величина смещения целиком клиентская.

### Ожидаемое влияние
Инструмент размещения (стартовый блок). Неограниченное смещение потенциально
позволяет вынести привязанную к нему призрачную структуру за штатные пределы
(размещение сквозь стены/вне зоны). Влияние ограничено ролью блока как
строительного помощника; на сервере не проверялось.

### Рекомендация по фиксу
Ограничить `CurPosOffset`/`CurRotOffset` разумным диапазоном на сервере.

## 7. OmniTool (Basic Transfer): перенос из произвольного контейнера от клиента

**Серьёзность: высокая** (при модифицированном клиенте). **Уверенность: по коду
высокая, на игре не проверено.**

### Затронутый код
`Items/OmniTool/BP_OmniTool.uasset`:
- серверное RPC `FiredEvent_Kav(Target, EventType, IsG, IsH, Mode_Index)`
  [Net/Server/Reliable] → `HandleFiredEvent` → `HandleMode_-_Basic` (режим
  `CurModeIndex == 1`, «Basic Transfer»).
- `HandleMode_-_Basic` → `SetSourceInventory(Target)` / `HandleBasicTransfer`.
- гейт `SanityCheckBasicTransfer`, диапазон `IsInventoryInRange`.

Это **одиночный** режим OmniTool («навёл-вытянул»). Массовый режим окна —
«Advanced Transfer» (`Transfer_-_DoTransfer` → `SP_DoBulkTransfer`) —
**безопасен**: сбор целей идёт через `InventoryFunctions.SP_GetNearbyInventories`
с жёстким гейтом `TargetingTeam == PC.TargetingTeam` и нативным
`AllowStructureAccess` на каждую структуру. Уязвим именно одиночный путь.

### Механизм
1. `Target` приходит от клиента в серверном RPC `FiredEvent_Kav`. Выбор цели
   трейсом (`DoClientFire` → `SP_LineTraceFromPlayer`) делается **на клиенте**;
   сервер свой трейс не повторяет и использует присланный `Target` как есть.
2. `HandleMode_-_Basic` берёт `Target.MyInventoryComponent` как источник (или
   цель) и ведёт перенос `HandleBasicTransfer` нативными `RemoveItem` +
   `AddItemObject`/`SP_FastGiveItem` — **в обход** штатной авторизации инвентаря
   ARK (`ServerRequestRemoveItems` / `RemoteInventoryAllowRemoval`).
3. Единственная серверная проверка — `SanityCheckBasicTransfer`: `IsValid` обоих
   инвентарей, `Target.bRemoteInventoryAllowAddItems`, `source ≠ target` и
   `IsInventoryInRange` (= `distance(источник, цель) ≤ PullRange`). **Нет**
   проверки `AllowStructureAccess`, `TargetingTeam`, владельца или пин-кода
   источника. Проверка — дистанция, не line-of-sight.
4. Кулдаун (`CheckCooldown`, `LastRequestTime` + `PullCooldown`) вызывается
   **только** в режиме Upload (Dedicated Storage); на Basic Transfer его нет.

### Ожидаемое влияние
Модифицированный клиент может подставить в `Target` любой контейнер/дино (не тот,
во что смотрит) и вытянуть содержимое себе, если он в пределах `PullRange`. Basic
бьёт по одному объекту за вызов, но без кулдауна и без team-гейта, поэтому клиент
может перебрать все контейнеры в радиусе → **кража содержимого базы в радиусе
`PullRange`, сквозь стены** (дистанция, не LoS), без права доступа. Под это
попадают чужие ящики, сейфы и сумки смерти (их `TargetingTeam` — команда
владельца, которую одиночный путь не сверяет). Контраст: массовый режим Advanced
то же «всё в радиусе» делает, но с team-гейтом.

Оговорки: нужен **модифицированный клиент** (ванильный шлёт только протрейсенную
цель) и физическая близость (в пределах `PullRange`, обычно десятки метров).
Ванильной игрой не воспроизводится. Количество при переносе зажимается корректно,
так что это **кража, а не дюп**.

### Рекомендация по фиксу
- В `SanityCheckBasicTransfer` прогнать владельца источника (и цели) через
  `AllowStructureAccess(PC)` + сравнение `TargetingTeam`, как это делает
  `InventoryFunctions.SP_GetNearbyInventories` на безопасном пути.
- Делать серверный ре-трейс от персонажа вместо доверия клиентскому `Target`.
- Применять `CheckCooldown` к Basic Transfer, а не только к Upload.

## Доп. защита Kav: токен сессии (SessionID) и `Cheater()`

Чего нет в оригинальном S+ и что Kav добавил поверх унаследованной логики —
анти-тампер на серверных вызовах OmniTool. Каждый клиент→сервер вызов несёт
целочисленный токен сессии; сервер сверяет его со своим `SessionID`, при
несовпадении зовёт `Cheater()`: кик игрока («You got Kicked for modifing your
mod files!!») и запись SteamID в серверный лог («Structures Kav: Player got
cought with modified Mod Files»).

Где применяется (всё в OmniTool/его баффе):
- `BP_OmniTool.FiredEvent_Kav`: `Mode_Index == SessionID`, иначе `Cheater()`.
- `Buff_StructuresPlus_OmniTool.BPServerHandleNetExecCommand`:
  `ExecParams.IntParam3 == SessionID`.
- серверное событие сканера: `ID == SessionID` (`ROS_Test`).

Как выдаётся токен: `GetSessionID` читает `SessionID =
BPGetExtraSpecialBlueprintInt(...)` — значение хранится на самом предмете
OmniTool, и сервер, и клиент берут его оттуда же.

**Оценка.** Это защита от «слепой» инъекции/реплея BP-событий: чит, шлющий
серверные RPC наугад без токена текущей сессии, ловится и кикается с записью
SteamID. Полезно против низкоусилийных пакет-читов. Но это **не граница
авторизации**:
- Токен лежит на предмете в инвентаре игрока; по штатной раскладке репликации
  предметов ARK он доступен клиенту-владельцу — модифицированный клиент читает
  свой же `SessionID` и штампует им запросы, проходя `Cheater()`.
- Даже с валидным токеном сервер в Basic Transfer не проверяет команду/владельца
  `Target` (находка #7). `SessionID` поднимает планку против скрипт-кидди, но
  кражу из чужого контейнера не закрывает.

Итог: доп. защита Kav осмысленна против массовых пакет-читов, но находку #7 не
нейтрализует — нужен team / `AllowStructureAccess`-гейт на источнике.

## Что проверено и не вызывает подозрений
- `BP_ItemTranslocator.SendItem`, `BP_BlueprintMaker.Convert`,
  новый `Handle Withdraw Amount` (Kav) — ищут/зажимают количество по факту
  в инвентаре/структуре на сервере. (`BP_OmniTool.HandleBasicTransfer` тоже
  корректно зажимает количество — дюпа нет — но не проверяет владельца
  источника: это находка #7, не «безопасно».)
- `BP_TekChemBench` (`CraftAll`) — `CraftAllInstant` вызывается только при
  `CanFullyCraft() && bIsBlueprint && !bAllowRemovalFromInventory` и пустом
  `BPAllowCrafting(PC)`; ресурсы проверяются.
- `BP_RepairStation` (`Repair`) — `RepairSelected` возвращает код ошибки,
  при нехватке ресурсов (код 2) ремонт не выполняется.
- `BP_Gate_Dynamic` / `BP_Gateway_Dynamic` — депозит материалов и возврат 50%
  при разборе (`BPOnStructurePickup`) соответствуют штатному поведению, дюпа нет.
- `BP_GrinderPlus` (`GrindItem`/`GrindAll`) — работает по собственному инвентарю
  гриндера, выдача ограничена `GrindGiveItemsPercent` и `MaxItemsToGivePerGrind`.
- `BP_Mannequin` (`FullMannequinUpdate`) — копирует только косметические данные
  (внешность/кости/виджет), предметов не двигает.

## Информационное (не уязвимость на боевом сервере)
`BP_CloningChamberPlus` (`StartCloneDino`, `GetCloningCost`) в Kav содержит ветки
по `IsShipping()`: вне shipping-сборки клонирование завершается за ~15 с и стоит
1 осколок. На выделенном сервере (shipping) не срабатывает — отладочный код.

## Открытые вопросы
- `SP_HandleResourcePull` (Pull из структур со счётчиком предметов, общий код
  S+/Kav) — порядок выдачи и списания в части с `IsStructureUsingItemCounts`
  вызывает вопросы при частичном прогоне, но поток не разобран до конца;
  не включено в находки до повторного разбора.
- Для находок 1 и 3 не установлено, при каких условиях `RemoveItem` реально
  возвращает `false` для «чужого» предмета (скорее всего ID не находится в
  целевом инвентаре) — зависит от деталей `BPFindItemWithID`/вызывающего кода,
  не проверено.

## Метод
